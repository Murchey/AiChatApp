# 03 数据模型与迁移

## 1. 数据库原则

- 所有时间使用 UTC 的 `TEXT`/ISO-8601 或统一的 epoch milliseconds，API 输出带 `Z`。
- 所有对外 ID 使用 UUID/ULID 字符串，不把 SQLite 自增整数暴露给客户端。
- 删除优先使用 `deleted_at`，因为同步和审核需要知道删除事件。
- 所有可变表保留 `created_at`、`updated_at`；需要排序的表另设明确排序字段。
- 用户生成内容必须有 `status`、`version` 或 `revision`，不要通过 NULL 猜状态。
- 不在一个 JSON 字段里藏关键查询字段；标签、作者、审核状态要有独立列或关联表。

## 2. V1 核心表

### `device`

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | TEXT PK | 设备 ID |
| `label` | TEXT | 用户给设备的名称 |
| `token_hash` | TEXT | 设备令牌哈希，绝不存明文 |
| `role` | TEXT | `USER` / `ADMIN` |
| `status` | TEXT | `ACTIVE` / `REVOKED` |
| `last_seen_at` | TEXT | 最近成功请求 |
| `created_at` / `updated_at` | TEXT | UTC |

邀请码兑换后只返回一次明文令牌。服务端保存 `HMAC(token, pepper)` 或 Argon2id 哈希，不能为了“方便调试”保存原文。

### `invite_code`

`id`、`code_hash`、`max_uses`、`used_count`、`expires_at`、`status`、`created_at`。兑换必须使用事务和条件更新，避免两个设备同时把剩余次数用超。

### `story`

`id`、`slug`、`title`、`author_name`、`summary`、`status`、`current_version`、`download_count`、`created_at`、`updated_at`。

`status` 至少包括 `DRAFT`、`PENDING_REVIEW`、`PUBLISHED`、`REJECTED`、`ARCHIVED`。客户端公共目录只查询 `PUBLISHED`。

### `story_version`

`id`、`story_id`、`version`、`content_json` 或 `file_path`、`content_sha256`、`content_size`、`schema_version`、`status`、`published_at`、`created_at`。

唯一约束：`(story_id, version)`。发布时只能从已校验版本切换为当前版本，不能覆盖历史版本。

### `story_tag`

`story_id`、`tag`，主键 `(story_id, tag)`。标签统一 trim、Unicode NFC、限制长度和数量；查询索引使用小写规范化列或在服务层规范化。

### `admin_audit_log`

`id`、`actor_device_id`、`action`、`resource_type`、`resource_id`、`request_id`、`metadata_json`、`created_at`。metadata 禁止存令牌和完整正文，保留摘要或哈希。

## 3. V2 预留表

### `comment`

`id`、`story_id`、`story_version`、`parent_id`、`author_device_id`、`body`、`status`、`like_count`、`created_at`、`updated_at`、`deleted_at`。

约束：`parent_id` 必须属于同一故事；深度最多 2 层；正文长度上限；审核状态 `PENDING`、`VISIBLE`、`HIDDEN`、`DELETED`。V1 可以建表但接口由 feature flag 关闭。

### `report`

`id`、`comment_id`、`reporter_device_id`、`reason_code`、`status`、`created_at`。同一设备对同一评论的未处理举报应去重。

### `story_revision`

用于管理员 App 发布：`id`、`story_id`、`base_version`、`draft_json`、`validation_result_json`、`author_device_id`、`status`、`created_at`、`updated_at`。发布成功后生成不可变 `story_version`。

### `sync_manifest` / `sync_object`

只在用户开启同步时使用。manifest 保存每个数据域的版本和哈希；object 保存加密后的压缩块。服务端不应能读取聊天正文，密钥由客户端派生。

## 4. Flyway 迁移规则

文件名只递增，例如：

```text
V1__baseline.sql
V2__add_story_tags.sql
V3__add_comments.sql
V4__add_story_revisions.sql
```

- 已执行的迁移禁止修改；修复请新增迁移。
- 每个迁移只做一件可回滚理解的事，并配一个空库和上一版本库测试。
- SQLite 不支持部分常见 ALTER TABLE；新增列、重建表、复制数据必须在事务中实现并验证行数。
- 启动时迁移失败应阻止服务接收请求，不要启动后才在第一个请求里报错。
- 数据目录备份先复制数据库文件到临时文件，再执行校验，避免复制到半写状态。

## 5. SQLite 索引

至少创建：

- `device(status, last_seen_at)`。
- `story(status, updated_at DESC)`。
- `story_version(story_id, version DESC)`。
- `story_tag(tag, story_id)`。
- `comment(story_id, status, created_at DESC)`（V2）。
- `admin_audit_log(actor_device_id, created_at DESC)`。

列表接口不能把所有故事或评论读入内存再分页；查询必须带 `LIMIT`，并用游标或稳定的 `(updated_at, id)` 做下一页。

## 6. 数据完整性检查

发布故事前必须校验：

- `schemaVersion` 是支持的整数。
- `storyId` 与 slug 一致，标题、摘要、标签、章节和记忆点有长度上限。
- 章节 order 唯一且连续或明确允许间隔；记忆点 ID 在整个包内唯一。
- JSON 文件大小、嵌套深度和总记忆点数量受限。
- SHA-256 与存储文件一致。

校验失败返回字段路径，例如 `chapters[1].memories[0].content`，不能只返回“格式错误”。
