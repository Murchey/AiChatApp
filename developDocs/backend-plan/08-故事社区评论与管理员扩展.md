# 08 故事社区、评论与管理员扩展

## 1. 与静态故事源兼容

当前 App 已支持 GitHub、Gitee、COS/OSS 的只读静态目录。服务器端故事接口必须继续返回兼容 `StoryCatalogEntry` 和 `StoryPackage` 的字段：

```text
index.json / GET /api/stories
  storyId, version, title, author, summary, tags, file, downloadCount?
stories/<id>/<version>.json / GET /api/stories/{id}/download
  schemaVersion, storyId, version, title, author, summary, tags, chapters
```

静态源没有下载统计、评论和点赞，客户端不能伪造这些字段。服务器源可以额外返回 `downloadCount`，字段缺失时客户端按 null 处理。

## 2. 管理员发布闭环

管理员从 App 发布故事时，不直接写 `story_version`，流程固定为：

```text
创建草稿
  -> 本地编辑章节/记忆点
  -> 上传草稿 JSON
  -> 服务端校验 schema、长度、ID、大小、重复项
  -> 返回 validationResult
  -> 提交审核
  -> 管理员确认发布
  -> 创建不可变 story_version
  -> 更新 story.current_version
  -> 写 admin_audit_log
```

每一步返回 `revision` 和 `updatedAt`。发布请求带 `baseVersion`；版本冲突必须让管理员重新加载，禁止覆盖其他管理员的版本。

App 端编辑器应提供：章节排序、记忆点排序、预览、字段错误定位、草稿保存和“仅保存草稿/提交审核/发布”三个明确动作。发布按钮必须在服务端再次鉴权，不能只依赖 UI。

## 3. 评论 V2

评论默认关闭。开启后：

- 只有已发布故事允许评论。
- 新评论状态为 `PENDING`，管理员审核后才 `VISIBLE`。
- 回复最多两层；客户端按父评论分组，服务端按游标分页。
- 删除采用软删除，展示“评论已删除”占位，避免破坏回复树。
- 评论、回复和举报均使用幂等键，重复提交不产生重复记录。
- 评论正文纯文本；链接不自动渲染为 HTML，必要时由客户端安全识别。
- 管理员可以隐藏、恢复、删除和查看举报原因；所有动作写审计日志。

未来若增加点赞，只增加独立 `comment_reaction` 表，不在 `comment.like_count` 上接受客户端直接写入；计数是服务端聚合结果。

## 4. 管理员从 App 发布的安全边界

- 管理员设备通过邀请码兑换后由服务端授予 `ADMIN`，客户端不能自行切换角色。
- 故事文件上传限制 MIME、大小、JSON 深度、章节数量和总记忆点数量。
- 文件名只允许服务端生成的 ID；客户端不能传绝对路径。
- 图片、音频若未来加入，文件进入对象存储，数据库只保存哈希和签名 URL，不把大二进制放进 SQLite。
- 发布接口不接受任意远程 URL；需要导入仓库时由服务端配置的白名单任务执行。
- 管理员可以撤回发布版本，但已安装到用户本地的故事记忆不应被远程删除；客户端显示“来源已归档”，由用户决定卸载。

## 5. 未来交互扩展顺序

1. 评论只读：拉取可见评论，不允许写入。
2. 评论创建 + 审核队列。
3. 回复和举报。
4. 管理员从 App 编辑草稿和发布。
5. 点赞、通知和统计（需要额外限流与隐私评估）。

每一步都必须保持故事详情、下载和角色安装逻辑可用；社区互动失败不能阻塞故事浏览。
