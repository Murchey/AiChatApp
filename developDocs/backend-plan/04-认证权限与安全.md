# 04 认证、权限与安全

## 1. 认证流程

### 设备邀请码兑换

1. 管理员生成一次性或限次数邀请码。
2. App 生成 `deviceId` 和随机 `deviceSecret`；deviceSecret 只保存在设备安全存储。
3. App 调用 `POST /api/invite/exchange`，提交邀请码和设备公钥/设备 ID。
4. 服务端校验邀请码、创建设备记录，返回一次性 `accessToken`、`refreshToken` 或可重新兑换的设备凭据。
5. App 只保存令牌，后续请求使用 `Authorization: Bearer <token>`。
6. 服务端只保存令牌哈希；退出设备或管理员撤销后立即失效。

如果没有设备安全存储，宁可只提供短期 access token，也不要把长期明文令牌写入普通 SharedPreferences。

### 令牌刷新和撤销

- access token 短时有效（例如 15 分钟）；refresh token 轮换并检测重放。
- refresh token 使用一次后作废，返回新的 refresh token。
- 同一设备发生异常刷新时，撤销该设备的所有 refresh token。
- 每个请求生成 `requestId`，错误响应和日志都带该 ID。

## 2. 权限模型

V1 角色只有：

- `USER`：浏览、下载、兑换后的设备操作。
- `ADMIN`：邀请码、故事草稿、校验、审核、发布、归档和审计读取。

不要只在客户端隐藏管理员按钮。每个管理员接口都在服务端做权限校验。未来可拆为：`MODERATOR`（评论审核）、`PUBLISHER`（故事发布）、`ANALYST`（只读统计）。

权限判断顺序：认证 → 设备状态 → 角色/权限 → 资源归属 → 业务状态。错误对外可统一为 `FORBIDDEN`，避免泄露资源存在性。

## 3. 限流和幂等

- 邀请兑换按 IP + 设备 ID 限流。
- 登录/刷新失败使用指数退避，不能让客户端无限重试。
- 故事下载统计接口必须支持 `Idempotency-Key`，重复请求不重复增加计数。
- 管理员发布使用 `Idempotency-Key`，同一草稿和同一版本重复提交返回第一次结果。
- 评论创建按设备和故事限速，V2 开启时再实现。

SQLite 单节点限流可先使用内存桶；多实例前必须迁移到共享 Redis 或数据库计数，否则每个实例都能绕过限制。

## 4. 输入与内容安全

- 所有 JSON DTO 使用 Bean Validation：长度、枚举、URL、分页上限、ID 格式。
- 故事正文和评论按纯文本处理；输出前做 HTML/Markdown 策略，禁止未经处理的 HTML。
- 限制请求体大小、压缩包大小、JSON 深度、数组长度和单字段 Unicode 字符数。
- 管理员导入文件先写临时目录，校验通过后原子移动；禁止路径穿越（`..`、绝对路径、符号链接）。
- 不允许服务端根据客户端传入 URL 抓取资源，避免 SSRF；COS/GitHub/Gitee 只用受信配置或白名单。
- 反向代理必须限制真实 IP 头来源，不能直接信任任意 `X-Forwarded-For`。
- 日志脱敏：Authorization、邀请码、API Key、设备令牌、聊天正文和完整评论正文禁止打印。

## 5. LLM 密钥策略

默认策略：App 直接调用用户选择的模型供应商，后端只保存模型能力配置和统计摘要。这样个人服务器泄露时不会导致用户 API Key 集体泄露。

可选中继策略：用户明确开启后，把一次请求的 provider、model、endpoint 和临时凭据通过 TLS 发送到后端；后端只在内存中使用，禁止写日志和数据库，响应结束后释放。中继必须有单用户限额和总请求体上限。

不要把“服务器地址 + 用户 API Key”误认为登录凭据。两者在权限、生命周期和日志策略上完全不同。
